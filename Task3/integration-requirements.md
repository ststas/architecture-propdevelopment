# Требования к внешним интеграциям: «Умный дом»

Документ описывает требования к интеграции с партнёрской платформой «умного дома» (интеллектуальный домофон и интеллектуальный шлагбаум), которая подключается к PropDevelopment через новый сервис `smart-home-gateway` в домене ЖКУ (см. [context-diagram.drawio](context-diagram.drawio) и обновлённую [PropDevelopment_С4_model.drawio](PropDevelopment_С4_model.drawio)).

Требования сформированы на основе двух источников:

- описанных проблем компании (нарушенный контроль данных, партнёрские API без единых политик безопасности и системного контроля передаваемых данных);
- разбора архитектурных решений и слабых мест `smart-home-gateway`, сделанного при проектировании диаграмм для этого задания.

## 1. Требования к безопасности

1. **Минимизация данных.** PropDevelopment не хранит биометрические шаблоны лиц и базу номеров автомобилей — эти данные остаются на стороне партнёра. `smart-home-db` хранит только ссылку на факт согласия/регистрации (enrollment id) и журнал событий доступа (кто, когда, какая точка, разрешено/отказано).
2. **Тот же уровень защиты для новой БД, что и для остальных.** `smart-home-db` подчиняется тем же требованиям шифрования в состоянии покоя и при передаче, резервного копирования и разграничения доступа, что и другие базы данных компании — новая интеграция не должна создавать ещё один неконтролируемый узел, как `auth-db-1` в текущей архитектуре.
3. **Ревью контрактов партнёра.** До подключения и периодически после — ревью API-контрактов партнёра на предмет объёма и категорий передаваемых персональных данных. Обоснование: в текущих партнёрских интеграциях компании уже зафиксировано, что «контракты API содержат категории данных, которые явно предоставляют персональные данные».
4. **Изоляция между объектами/УК на стороне партнёра.** Требование к партнёру — техническая и договорная изоляция данных между разными зданиями/собственниками/управляющими компаниями, с проверкой (аудит или пентест) до запуска в продакшен. Обоснование: у существующих партнёров ЖКХ уже отмечен случай, когда «партнёр из одной управляющей компании может увидеть или изменить данные клиентов и жилищных комплексов, которые относятся к другой компании» — для сервиса, управляющего физическим доступом, такая ошибка недопустима.
5. **Минимальные привилегии партнёрского доступа.** Партнёр может выполнять только те действия и получать только те данные, которые прямо необходимы для домофона/шлагбаума (открытие конкретной двери/шлагбаума, передача событий по конкретному объекту) — без возможности запросить данные по чужим объектам.
6. **Скоуп и ротация секретов.** Учётные данные интеграции (OAuth2 client credentials, mTLS-сертификаты) должны быть выданы отдельно как минимум на уровне ЖК/здания, а не единым секретом на весь портфель объектов, и поддерживать быстрый отзыв/ротацию при подозрении на компрометацию.
7. **Защита от повтора событий.** Webhook-события от партнёра проверяются не только по подписи (HMAC), но и по временной метке/nonce, с идемпотентной обработкой на стороне `smart-home-gateway` — иначе перехваченное сообщение «шлагбаум открыт» можно воспроизвести повторно.
8. **Политика поведения при потере связи.** Для каждого типа устройства заранее определено поведение при недоступности партнёра или сети (fail-open/fail-closed), отдельно для домофона (с учётом требований к аварийной эвакуации) и для шлагбаума — это не должно решаться по умолчанию поведением библиотеки или устройства.
9. **Защита видео/аудио-потока вызова.** Маршрутизация видеозвонка домофона должна дополнительно проверять принадлежность потока конкретному собственнику/квартире перед показом в приложении. Обоснование: у компании уже зафиксирована жалоба, что в личном кабинете «иногда могут отображаться данные другого клиента» — ошибка такого рода в видеопотоке двери гораздо серьёзнее.
10. **Юридическая оценка обработки биометрии.** Обработка данных распознавания лиц требует отдельной юридической оценки на соответствие 152-ФЗ (ст. 10, специальные категории персональных данных) независимо от архитектурного решения по минимизации хранения — снижение объёма хранимых данных не заменяет эту оценку.
11. **Надёжный отзыв доступа.** Отзыв доступа у партнёра при смене или прекращении права собственности на объект должен быть операцией с гарантированной доставкой (повтор при сбое + оповещение ответственных при повторных неудачах), а не разовым вызовом без обработки ошибок — иначе прежний собственник может неопределённо долго сохранять физический доступ.
12. **Журналирование и мониторинг обращений.** Все вызовы партнёрского API в обе стороны логируются; аномальные всплески команд (например, много запросов на открытие за короткое время) должны формировать оповещение.

## 3. Организация взаимодействия систем предприятия с внешней платформой

- **Единая точка интеграции.** Весь трафик к партнёрской платформе и от неё идёт только через `smart-home-gateway`. Ни мобильное приложение, ни другие сервисы домена ЖКУ не обращаются к партнёру напрямую — это даёт компании одну точку, где применяются политики безопасности, логирование и мониторинг, вместо нескольких неконтролируемых прямых интеграций (как сейчас устроено взаимодействие с поставщиками ЖКХ и платёжной системой).
- **Разделение команд и событий.** Исходящие команды (открыть дверь/шлагбаум, зарегистрировать лицо/номер) и входящие события (звонок, распознавание) идут разными каналами с разными механизмами аутентификации — это позволяет независимо ужесточать или проверять каждое направление.
- **Привязка к жизненному циклу собственника.** `smart-home-gateway` получает от `tenant-core-app` информацию о статусе собственника и инициирует отзыв доступа у партнёра при смене или прекращении права собственности, с гарантированной доставкой этой операции.
- **Явная деградация при сбоях.** Поведение при недоступности партнёра или сети определено заранее и раздельно для домофона и шлагбаума, а не оставлено на усмотрение реализации по умолчанию.
- **Минимизация данных на границе интеграции.** Через границу с партнёром не передаются и не хранятся у PropDevelopment биометрические шаблоны и номера автомобилей — только ссылки на согласие/регистрацию и факты событий доступа.

**Рекомендация вне рамок этой задачи.** Тот же паттерн (единый шлюз, минимизация данных, единые политики безопасности) стоит в перспективе распространить на существующие интеграции с поставщиками ЖКХ и платёжной системой — сейчас они подключены к `tenant-core-app` напрямую, без единой точки контроля, что и было отмечено как одна из двух главных проблем компании.
